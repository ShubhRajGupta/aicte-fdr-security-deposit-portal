# Six-slide SIH idea deck: approach-first blueprint

Always use the current official template headings. This is a content strategy, not permission to change the template.

## Slide 1 — Title page
**Purpose:** correct submission identity, project name and visual anchor—not a problem analysis.

**Partitions inside existing regions:**
- metadata panel: official PS ID/title, theme/category, Team ID, registered team name;
- project identity/visual panel: project acronym + an explanatory technical visual if the template allows.

Rules: exact PS metadata from official source; team name `Phra Uma Thewi`; current Team ID only; numeric citation for PS metadata. Preserve header/footer/logo geometry.

## Slide 2 — Proposed solution
**Purpose:** explain what the team will build and the operating logic.

**Partitions:**
1. solution name `HINDI WORD — Full Technical Expansion` + one-line technical fragment;
2. large numbered workflow / user journey / solution mechanism diagram;
3. short differentiator and maturity-status panel.

Content: target operator/user, input → processing → action/output, 3–5 genuine differentiators, actual prototype status, source markers for existing methods/alternatives. No paragraph summarizing the PS.

## Slide 3 — Technical approach
**Purpose:** demonstrate that the solution has a credible technical design.

**Partitions:**
1. large architecture/data-flow/deployment diagram;
2. compact technology/method table (`component | choice | reason | evidence/source`);
3. protocol/API/data/security/fallback notes or test artifact.

Content: numbered path, system boundaries, external dependencies, data provenance, integration and failure handling. Cite research, frameworks, specifications and datasets next to the relevant claims.

## Slide 4 — Feasibility and viability
**Purpose:** show buildability, maturity and practical deployment constraints.

**Partitions:**
1. MVP roadmap/maturity gates (`now → hackathon → pilot/scale`);
2. compact resource/dependency table;
3. risk → mitigation → fallback table;
4. validation criteria (if space and template allow).

Content: demonstrated vs planned; timeline/roles if known; permission/data/hardware needs; power/network/accessibility/maintenance/procurement constraints; failure criteria and fallback. No false deployment claims.

## Slide 5 — Impact and benefits
**Purpose:** connect engineering to real people, existing workflows and measurable outcomes.

**Partitions:**
1. `beneficiary/workflow → intervention → outcome` matrix;
2. strong visual (authentic prototype or relevant field image, workflow, map or data-derived chart);
3. metric/evidence/limitations panel.

Content: sourced operational reality, field evidence only if genuine, baseline vs target vs observed result, social/economic/environmental benefits only when relevant, scale assumptions and risks. Never invent interviews or outcome percentages.

## Slide 6 — Research and references
**Purpose:** demonstrate evidence maturity and make every major claim verifiable.

**Partitions:**
- group sources into official/ground-reality sources, technical papers/standards, open-source frameworks/data/API, and images/datasets where applicable;
- use compact columns or tables without microscopic text;
- resolve all citation markers used on slides 1–5.

Each entry: author/organization, title, year/date, venue or dataset/version where applicable, DOI/direct URL, access date if useful. References should support actual slide claims, not pad the page.

## Non-negotiable narrative rule
Only slide 1 is allowed the minimum metadata required to identify the PS. Slides 2–5 should concentrate on approach, research, real-world fit, architecture, maturity, validation and measurable outcomes. If a fact about the challenge appears, immediately connect it to a design decision or test.
