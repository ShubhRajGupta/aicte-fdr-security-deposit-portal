# Typography, partitions and information density

## Fixed geometry from the sketch
Keep the top reserved band and bottom reserved band untouched. Use the middle body as the main content canvas, internally divided into a dominant panel and supporting panel(s). Default to a larger technical visual/explanation and a narrower keypoints/evidence panel. The actual official PPTX defines the real measurements.

## Arial hierarchy

| Role | Typeface | Target size | Use |
|---|---|---:|---|
| H1 | Arial Bold | 30–36 pt | Existing slide title area; do not move it |
| H2 | Arial Bold | 18–22 pt | Panel heading / technical section |
| Body | Arial | 14–17 pt | Short exact keypoints, numbered method |
| Diagram/table label | Arial | 11–14 pt | Module name, metric, stage, comparison |
| Caption/source marker | Arial | 8–10 pt | Figure/source note; must remain readable |

If the official template already locks a specific title size, preserve the title box and hierarchy. No content box may be stretched outside the available region; shrink or reshape content only inside its existing region. Use Arial for editable text. Do not attempt to replace text embedded inside an official logo image.

## Mandatory partition rule
Every slide must have visible divisions within the existing body region. Use at least two partitions where content allows:
- large diagram + right-side method/evidence panel;
- numbered workflow + differentiator panel;
- architecture + technology-to-reason table;
- implementation roadmap + risk/mitigation matrix;
- beneficiary/outcome matrix + source-backed metric panel;
- two-column grouped references.

Reserve top and footer bands exactly as in the template. Avoid touching fixed branding, title fields, page numbers and footer text. Never copy pixel positions from the sample sketch blindly.

## Maximize content without illegibility
- Target approximately 85–95% use of the available body area for useful content on information-rich slides.
- Prefer 2–4 partitions per slide; a partition should have one message, a short H2 and an informative diagram/table/2–5 fragments.
- Use a substantial relevant visual on solution/technical/feasibility/impact slides where it clarifies the method or reality.
- Put the most important diagram in the largest available body region; use a support panel for sources, parameters, decisions, metrics, risks or evidence.
- Use a dense table when comparing systems, technologies, risks, stages or acceptance criteria. Keep cell text brief.
- If a slide feels empty, add real architecture, implementation evidence, a useful comparison, a grounded constraint or an evaluation method. Do not add restated problem text or generic stock images.
- If it feels crowded, remove duplication and low-value claims; do not immediately reduce all type sizes.

## Emphasis and color
- Use official template palette as base; no rebranding or theme replacement.
- Bold the key technical terms and decisions.
- Use underline/highlighter effect on very few high-value items.
- Use accent text color for state/status or key output only; also use a label so color is not the sole signal.
- Number workflow/method stages `01`, `02`, `03`; keep numbering consistent.
- No emoji glyphs. Use standard arrows, lines, borders and shapes.

## Visual literacy
- Images should document an actual prototype/environment or illustrate a sourced real condition; label illustrative imagery honestly.
- A diagram needs a legend only when symbols are not self-evident. Label arrows, boundaries, external dependencies, data input/output and important failure/fallback paths.
- Chart labels need units, baseline, sample/timeframe and source. Never make a metric image without the underlying verified value.
- Do not use a tiny screenshot full of unreadable text. Crop to the relevant interface and provide a short callout.
- Do not intentionally split words, abbreviations or the team name. Team name exactly `Phra Uma Thewi`.
